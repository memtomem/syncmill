# Memory (`memory.py`)

> Design record for `memory.py`, moved verbatim from `CLAUDE.md`. `CLAUDE.md` keeps a
> short rule list for this module; this file holds the full reasoning, history and test map.

`SyncmillMemory` applies syncmill conventions over the selected `MemoryBackend`: namespace `agent-runtime:{agent_id}` is private per agent and `shared` is the cross-agent knowledge base. The Supervisor is the **sole reader/writer** — there is intentionally no MCP sharing between agents. Backend APIs are async, as is the agents' `aexecute` path, while orchestration stays sync. `run_async()` bridges both into that sync world by **reusing a module-level event loop**; do not switch to `asyncio.run()`, which closes resources needed by later calls. `close_event_loop()` releases it at CLI shutdown.

**Multi-agent API semantics (memtomem-aligned):** syncmill now mirrors memtomem's MCP multi-agent tools through the backend contract — the MCP tools themselves are MCP-SDK-coupled, so `MemtomemBackend` reproduces their semantics on the `MemtomemStore` surface + the sanctioned storage privates (never `import memtomem.server.*`, and never `start_agent_session`, whose bound agent id would OVERRIDE the explicit namespace filter and break board scoping). Four pieces: (1) **Unified search** — `search_context` is ONE `search_multi` call over `[agent-runtime:{id}?, shared, global-shared?]` (`_CONTEXT_TOP_K` rows; the agent namespace joins only when a caller passes `agent_id`, and no strategy or room does today, so an unscoped run's prompts are enriched from `shared` alone, and a board-scoped run's from its `board-run:{run_id}` scope plus global `shared`); memtomem gets a single native comma-union merged-ranking call (`mem_agent_search`'s `include_shared` shape), mem0/LangGraph an adapter-side per-namespace merge (`BackendCapabilities.native_multi_namespace_search`). (2) **Provenance shares** — an unscoped `share_result` is a two-step agent-share: `add_returning_ids` into the producer's `agent-runtime:{id}` (replicating `MemtomemStore.add`'s guard→sidecar-lock→mix-refusal→`append_entry`→`index_file(lock_held=True)` flow to keep `IndexingStats.new_chunk_ids`, which `add` discards; the lock span is memtomem's write-locking contract (since 0.4) — an unlocked append lets the watcher index the new file first WITHOUT the explicit namespace, stranding the agent-private chunk in `default`, so mix-guard, append and re-index share ONE cross-process sidecar-lock span (the real smoke pins it) — so strategy intermediates now populate the agent namespaces — a provenance record; no current caller passes `agent_id` to `search_context`, so these originals are not read back into prompts), then `share_chunk` COPIES **every** chunk to `shared` (a long result splits — sharing only the first chunk would drop the output half) with the collapsed `shared-from=<id>` tag + a best-effort `chunk_links(link_type="shared")` row (`share_provenance_links`). A failing step falls back to the direct `shared` add **and degrades** (the lost provenance contract is surfaced, never silent), but a PARTIAL share (some chunks copied, some not) degrades **without** the fallback — those chunks are already in `shared`, so a full direct copy beside them would inflate `shared_stats` and feed near-duplicate rows to every reader; a `WriteBlockedError` (redaction guard) skips the fallback — the same guard would re-block. A board-scoped view always writes directly (both namespaces collapse to the scope — the leak guard is untouched, and D4's union-read rides the same `search_multi` namespace list). **Two MCP-parity details are load-bearing:** each write invalidates the search pipeline's TTL result cache (the MCP add path does; `MemtomemStore.add` does not — without it an intra-run pipeline/council/decompose handoff can be served the pre-write cached result), and **every** write — `add` and `add_returning_ids` alike, since `add` now routes through the same flow — goes to a **namespace-suffixed daily file** (`{date}.{ns}.md`, `:`→`.`) because under default memtomem config re-indexing one file holding the same content-hash twice collapses to the last write — the two-step's identical copy would DELETE the private original and orphan the link (a real FK failure the opt-in smoke caught). Routing `add` through `MemtomemStore.add`'s namespace-SHARED `{date}.md` was the same bug in a second costume: `delete_by_namespace` removes DB rows only while the markdown is what the index is rebuilt FROM, so a GC'd `board-run:*` chunk survived in a file a later `shared` write re-indexed — and, its rows gone, was treated as new and stamped `shared`, leaking board-internal content into global knowledge. `delete_board_runs` prefers the optional `purge_namespace(ns)` capability: the memtomem adapter locks the namespace before writers select a day file, acquires every owned source's real L2 sidecar, removes sources before rows, and invalidates its local search cache. It recognizes exact legacy and native day-file names across all index roots. Unprovable or incomplete deletion raises and remains retryable; file-less adapters retain their row-delete fallback. Purge admission caps source locks at 256 and checks process descriptor headroom; the GC loop has a cooperative 30-second budget. Native memtomem writers do not share the namespace lock, so the final scan detects some races but cannot exclude a later external write. **Known residue:** a store written before this change kept every namespace in one shared `{date}.md`, whose entries carry no namespace — nothing selects them, and deleting the file would take shared knowledge with it, so pre-upgrade scratch stays re-indexable and is a manual cleanup. **A third parity detail is load-bearing:** every write passes an EXPLICIT unique heading (`_entry_title` — ms timestamp + full uuid) instead of relying on `append_entry`'s default. Under memtomem 0.3 that default was `## Entry {now}` at SECOND resolution (0.4's default is now ms + full uuid, but the explicit title keeps the pinned deterministic shape from drifting with the upstream default), and two entries sharing a heading in one file re-chunk into a SINGLE chunk — so a second write inside the same second swallowed the first entry's text and re-minted its chunk id, which `add_returning_ids` had already returned, making the two-step share look up a chunk that no longer existed and silently fall back to a direct write with the provenance link gone. Back-to-back writes to one namespace are exactly what a pipeline/council/decompose handoff does, so this was live, not theoretical (the real smoke's `rapid write` block pins it; only the real store re-chunks, so the hermetic fake can pin the unique heading but never the consequence). Milliseconds alone would only narrow the window, hence the uuid suffix; the `> created:` line memtomem's own parsers read keeps its second resolution. **The unique heading only reaches content that does not open with `## `** — `format_entry_block` treats heading-led content as supplying its own heading, skips the title entirely, and in that branch emits the tags blockquote BEFORE the content's heading. syncmill's payloads used to open with `## Task Result` / `## Board Item Result`, so this was not a same-second window at all: EVERY result carried the same heading, consecutive results merged into one chunk, the returned ids were re-minted, and the survivor's tags landed in the previous entry's section — leaving it unreachable by `tag_filter`, the documented retrieval key for kind-tagged artifacts. Both payloads therefore label themselves in **bold** (see memory.py's heading note; a hermetic test pins the shape, `add_returning_ids` warns if a heading-led payload ever returns, and the real smoke now uses the PRODUCTION payload shape — exercising plain text there passed while every orchestration write was broken). **Residue:** a bold label is not enough if the BODY carries headings — agent output is embedded verbatim, so an agent writing `## Summary` still opens a section two runs can share. Closing that needs either mutating the agent's text (the backend contract is verbatim storage) or an upstream chunker change. (3) **Registration metadata** — `register_agent` upserts `mem_agent_register`-style description/color via `register_namespace` (unconditional; `_AGENT_COLORS` supplies defaults; `None` = default, explicit `""` = clear, passed verbatim), keeping `ensure_namespace`'s create-if-missing for `shared`. (4) **Kind-tagged artifacts** — every share carries `[kind, agent_id, task:{task.id}]`: the winner is `task-result`; strategies tag intermediates `pipeline-stage` / `council-proposal` / `council-critique` / `decompose-subtask`, and Decompose publishes its **parsed** plan as `decompose-plan` (what actually runs after normalization/capping — never the raw planner response, never the degraded whole-task fallback) — so unified search surfaces work plans/results and `tag_filter` retrieves one artifact class exactly. Requires `memtomem>=0.6.8,<0.7` (the upper bound because the replicated add flow rides privates — bump it only WITH the required real smoke `SYNCMILL_TEST_MEMTOMEM_REAL=1`, which includes a store written by real memtomem 0.4.0 and reopened under the pin). The 0.6 port mirrors upstream's own add on its derived target: `require_user_base(memory_dirs, project_memory_dirs)` without `allow_project_tier` (syncmill writes unattended and has no consent gate for a git-tracked tier), the L2 sidecar keyed by `memory_lock_path` (the resolved path the indexer keys on — upstream #2130), and an append refused for a symlinked day file, a non-`user` tier (upstream's `_resolve_target_scope`), a read-only source or an excluded one. `purge_namespace` refuses — before deleting anything — a candidate in a `read_only_memory_dirs` root (0.6's `all_index_roots` includes them) or in a `project_shared` tier. memtomem's own transaction leaks (scratch_cleanup after `end_session`, a failed `add_chunk_link`) are fixed upstream since 0.5 (#2168/#2171); the real smokes keep both as regressions. memtomem 0.4+ forces `mcp>=2.0.0,<3` (the fastmcp module is removed in the 2.0 SDK — see the gateway section), so the two pins move together.

**One lock span per share (#117).** The two-step provenance share used to be two independent lock → append → index sequences: `add_returning_ids` took the agent namespace's lock and its day file's sidecar for the original, released both, and then each `share_chunk` took `shared`'s lock and sidecar again for ONE chunk's copy and re-indexed the whole `shared` day file for it. So another writer of either namespace could land between a share's halves, and a share of an N-chunk result paid N full re-chunks of a day file that grows with every write that day (`index_file` is about 80% of a share's cost on the real store). `MemtomemBackend.add_and_share` replaces both with one span: it takes both namespace locks, reads the clock ONCE (so the original and its copies never straddle a date rollover), names both day files, runs the protected-target refusals on both, takes both files' sidecars, re-runs the refusals, and then, inside the span, does mix → append original → index; reads each fresh source chunk; guards every copy; mix → append every copy → ONE index of the `shared` file; links each copy; and invalidates the search cache once. Every write-path invariant above holds per file (namespace lock before the day file is selected, the sidecar across mix-check → append → index, explicit unique headings, bold-led payloads, the refusals). Copies are attributed back to their source chunk by the collapsed `shared-from=<source id>` tag each carries, never by position in the index result, so a copy that re-chunks into two links both, and a stale entry the index picks up from the same file (an append whose writer died before indexing) is never counted as a copy. The two-call path had that last edge wrong: it linked whatever the copy's index returned. The result is `SharedWrite(source_ids, shared_ids)`, aligned per source chunk, with `None` exactly where `share_chunk` would have returned `None`, so `SyncmillMemory._provenance_share` feeds `share_result`'s unchanged healthy / partial-without-fallback / raising-falls-back / `WriteBlockedError`-skips-fallback rules from either path. One deliberate difference: every copy is guarded before any is appended, so a blocked copy leaves the original and no copies, where the two-call path could have written the earlier copies first. `SyncmillMemory` uses the span only when `BackendCapabilities.single_span_share` is set AND the method exists (default off, so a third-party adapter keeps the two calls); mem0 and LangGraph keep the adapter fallback, since they have no file locks to merge and no per-file re-index to batch. Strategy-layer calls are untouched: still serial, still between fan-outs. Measured with `scripts/bench_share_span.py` (real `CouncilStrategy` with fake agents over a real store: 3 members, 2 rounds, 9 shares per run, 5 alternating repeats, median share time per run, two-call → single span): fresh store 0.272 s → 0.101 s (−63%); a `shared` day file already holding 400 entries 1.692 s → 0.399 s (−76%), the gap growing with the file because each per-chunk copy re-chunked all of it; a background writer to `shared` every 50 ms 0.332 s → 0.109 s (−67%); two councils at once in two processes 0.360 s → 0.270 s for one and 0.750 s → 0.194 s for the other. A tight-loop writer (no pause between writes) starves any poller with memtomem's 50–500 ms backoff, so it measures luck rather than the lock; it still favoured the span (4 repeats: median 48.9 s → 3.7 s, ranges 6.9–79 s vs 0.1–10.5 s) because a share now makes one contended acquisition instead of one per chunk.

**Lock ordering rule** (written on `_namespace_lock_path`, followed by every acquirer in `memory_backend.py`): (1) levels: every syncmill namespace lock a span needs is taken before any memtomem L2 sidecar, and no namespace lock is ever taken while a sidecar is held; L2 then nests above memtomem's own L3/L4 exactly as upstream orders it. (2) Within a level, ascending `str(lock_path)` after deduplication: `_namespace_lock_order` for namespace locks, `sorted(..., key=str)` over `memory_lock_path` for sidecars (upstream's L2 multi-acquire rule). Deduplication matters because `async_file_lock`'s in-process layer is not re-entrant. A share takes 2 + 2, a write 1 + 1, and a purge 1 + its sources' sidecars, all in that one total order, so no wait-for cycle can form between two shares (including the same pair of namespaces in opposite roles), a share and a write, or a share and a purge. The one acquirer that bends (2) is a purge's re-snapshot pass, which can add a sidecar sorting below one it holds. That stays safe because every sidecar a purge takes belongs to its own namespace, whose lock it holds, so the only other holder possible is a memtomem indexer: it holds one L2 and never waits for a second. Tests: the hermetic adapter tests pin the acquisition sequence and per-level order; `test_real_share_span_takes_every_lock_before_writing_anything` shows a held `shared` lock or sidecar stops the share before the private original is written; and `test_process_writers_cannot_land_inside_one_share` (with `test_process_two_call_share_leaves_the_window_open` as its contrast) shows, across real processes, that writers of either namespace wait for the whole share instead of landing between its halves.

**Memory is advisory/best-effort.** Every `SyncmillMemory` method catches its own exceptions, logs a warning, sets `degraded`/`last_error`, and returns a safe default. A broken or misconfigured backend must never abort a task — the agent still runs, just without shared context. Preserve this when editing memory or the Supervisor; the CLI surfaces `supervisor.memory.degraded` as a yellow notice. memtomem applies `~/.memtomem/config.json` last and shares its global DB by default; mem0 and LangGraph use separate stores unless configured otherwise, with explicit staged migration available between every installed backend pair.
