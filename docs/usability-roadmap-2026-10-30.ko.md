## 근거: 사용성 평가

안전성과 신뢰성은 강하다. 격리 워크트리, 명시적 apply, 품질 게이트, lease 펜싱,
실패 시 안전한 저하가 이를 뒷받침한다. 반면 처음 쓰는 사람이 첫 검증된 변경까지
가는 길에는 걸림돌이 많다.

| 걸림돌 | 현재 상태(이 브랜치 기준 확인) |
| --- | --- |
| 진입 장벽 | 숨겨지지 않은 최상위 명령 23개, `run`의 긴 옵션 14개, `tui` 탭 7개 |
| CLI 설치·인증 부담 | 실제 실행에는 `claude`/`codex`/`kimi` 설치와 로그인이 필요하다. `doctor`가 인증 상태를 확인하지만 체험 경로는 없다. |
| 기본값으로 꺼진 기능 | 보드, 실행 보고서, 트레이스, 품질 게이트, 브레이커가 기본으로 꺼져 있다. `doctor`는 이 기능들의 상태나 켜는 법을 보여 주지 않는다. |
| 비용·시간 가시성 | `run --dry-run`의 `RunPlan`이 에이전트, 최대 에이전트 호출 수, 게이트 명령을 보여 준다. 타임아웃과 메모리 위치는 보여 주지 않고, 실행 전 확인 단계에 연결되어 있지도 않다. |

학습 자료(`docs/notebooks/`, 사용자 가이드의 `init → doctor → dry-run → run → diff →
apply` 흐름)는 이미 있다. 부족한 것은 학습 자료에서 실제 작업으로 넘어가는 다리다.

## 1. #110 — 닫기 제안

[#110](https://github.com/memtomem/syncmill/issues/110)이 요구한 원자적 namespace purge는
이미 들어가 있다. `MemtomemBackend.purge_namespace`가 writer 잠금을 쥔 채 소스와 행을
지우고, `SyncmillMemory.delete_board_runs`는 백엔드가 이 메서드를 제공하면 그것을 쓴다.
two-sweep 방식은 이 메서드가 없는 백엔드의 대체 경로로만 남았다. 남은 한계(다른
프로세스의 검색 캐시, symlink source, 검증되지 않은 동시성 시나리오 3개)는
[#112](https://github.com/memtomem/syncmill/issues/112)가 이미 추적한다.

닫을 때 남길 코멘트 초안:

> 원자적 purge는 #111로 구현되었습니다. memtomem 백엔드에서는 `delete_board_runs`가
> `purge_namespace`를 사용하며, two-sweep은 이 메서드가 없는 백엔드의 대체 경로로만
> 남아 있습니다. 남은 한계(교차 프로세스 캐시, symlink source, 다중 프로세스 테스트)는
> #112에서 이어서 추적하므로 이 이슈는 닫습니다.

완료 조건: 위 내용을 확인한 메인테이너가 `state_reason=completed`로 닫는다.

## 2. #171 — `syncmill start`와 오프라인 체험 (최우선)

[#171](https://github.com/memtomem/syncmill/issues/171). 목표는 설치 직후 5분 안에
"변경 → 검증 → diff → apply"를 한 번 끝까지 경험하고, 같은 입구에서 실제 작업으로
넘어가는 것이다.

### 제안 범위

- **입구:** `syncmill start` 하나. 기존 고급 명령은 그대로 둔다. 실행 계획은
  `planning.build_run_plan`과 기존 run/room 경로를 그대로 재사용한다. 따라서 dry-run과
  실제 실행이 같은 계획을 보여야 한다.
- **오프라인 체험:** 가짜 에이전트로 임시 Git 저장소에서 변경 → 검증 → diff → 명시적
  apply까지 진행한다. 로그인, 실제 provider 하위 프로세스, Jupyter, 소스 체크아웃,
  사용자 홈의 저장소 접근이 모두 필요 없어야 한다. `docs/notebooks/_sandbox.py`의
  접근을 패키지 안의 도우미로 옮기는 것이 출발점이다.
- **실제 작업은 두 갈래만:**
  - "단일 에이전트": 일반 단일 에이전트 실행
  - "두 후보 비교": Room으로 두 후보를 만들고 비교·선택
- **실행 전 표시:** 사용할 에이전트, 검증 명령, 최대 호출 수, 타임아웃(그리고 메모리
  위치). 비용은 알 수 없으면 "알 수 없음"으로 표시한다. 호출 수를 달러 예산이나
  provider 내부 도구 호출 상한처럼 보이게 하지 않는다.
- **에이전트가 하나뿐이면** 비교를 조용히 시작하지 않고 단일 실행을 제안한다. 0개면
  체험과 설치·인증 안내만 제시한다.
- **검증 명령:** 저장소를 읽기만 해서 후보를 찾아 보여 주고, 사용자가 고른 뒤에만
  실행한다. 탐색 중에 저장소 스크립트를 실행하지 않는다. 게이트가 없으면
  "검증되지 않음"으로 남긴다.
- **비대화형 환경(TTY 없음):** 무한정 기다리지 않는다. 필요한 입력을 명시적으로
  받거나, 빠진 값과 이에 해당하는 기존 명령을 안내하고 끝낸다.

### 합의된 결정 (2026-10-30, 메인테이너와 확정)

| # | 결정 | 내용 |
| --- | --- | --- |
| 1 | 명령 형태와 범위 | `syncmill start` 하나. 대화형 메뉴에서 "체험해 보기 / 내 프로젝트에서 작업"을 고르고, `--trial`은 메뉴 없이 바로 체험한다(TTY가 없어도 쓸 수 있음). 1차는 CLI만이며, TUI 진입점은 같은 계획 조립 코드를 재사용해 2차에 붙인다. |
| 2 | 오프라인 체험 | 버그 하나(`add(2, 2) == 5`)가 있는 작은 저장소에서 가짜 에이전트 두 개가 후보를 만든다. 하나는 검증을 통과하고 하나는 실패한다. 검증 명령은 표준 라이브러리 `python -m unittest`. 비교 → diff → 확인 후 apply까지 진행한다. 상태는 모두 임시 디렉터리에 두고 끝나면 지우며, `--keep`이면 경로를 남긴다. 끝나면 요약과 "내 프로젝트에서 해 보려면" 다음 명령을 보여 준다. |
| 3 | 두 후보 비교 | Room으로 실행하고, `start`가 비교 화면(후보별 검증 결과, 변경 규모)에서 diff 보기와 적용까지 이어서 안내한다. 중단하면 `syncmill room compare <id>`로 이어 가는 방법을 보여 준다. 체험도 같은 경로를 쓴다. |
| 4 | 실행 전 표시 | `start`가 확인 화면을 직접 조립한다. 방식, 에이전트와 각 타임아웃, 최대 에이전트 호출 수, 검증 명령, 메모리 위치, 비용("알 수 없음")을 보여 준다. `start --dry-run`은 같은 화면을 출력하고 아무것도 실행하지 않는다. `RunPlan`과 manifest 형식은 바꾸지 않는다. |
| 5 | 검증 명령 | 알려진 표식의 고정 표로 후보를 찾는다: `pyproject.toml`(pytest) → `python -m pytest -q`, `package.json`의 `scripts.test` → `npm test`, `Makefile`의 `test:` → `make test`, `Cargo.toml` → `cargo test`, `go.mod` → `go test ./...`. 파일은 읽기만 하고, 항상 "직접 입력"과 "검증 없이"도 고를 수 있다. 고른 명령은 "다음에도 쓸까요? | 6 | 준비 상태와 예외 | 준비 판정은 `doctor`의 확인(실행 파일, claude/codex 로그인 상태)을 함수로 분리해 함께 쓴다. 로그인되지 않은 에이전트는 해결 명령과 함께 제외한다. 준비된 에이전트가 0개면 체험과 설치·로그인 안내만, 1개면 단일 실행을 제안한다. 3개 이상이면 우선순위 상위 2개를 기본으로 쓰고 확인 화면에서 바꿀 수 있다(비대화형은 `-a` 두 번). dirty 저장소는 "커밋하지 않은 변경 N개를 포함해 시작하며, 적용 전에 그 파일을 바꾸면 적용이 거부될 수 있다"고 알리고 확인 후 진행한다. 실행 전 취소는 아무것도 바꾸지 않고, 라운드 중 취소는 `syncmill room show <id>`로 이어 가는 법을 안내한다. |
| 7 | 성공 기준과 측정 | 1차 제품에는 계측을 넣지 않는다. 사람 시간은 진행자가 있는 사용성 세션(같은 과제, 기존 명령 대 `start`)으로 재고, 설계는 #190과 함께 한다. 체험이 끝까지 도는지는 hermetic 테스트로 매번 확인한다. 성공은 "검증 상태를 이해하고 의도한 저장소에 적용"이다. 검증 없이 적용한 경우도 그 사실을 분명히 보여 주었다면 성공으로 세되, "검증된 적용"과 "검증 없는 적용"을 나눠 보고한다. |
| 8 | 꺼진 기능 안내 | #171과 별도로 먼저 낸다(3절). `start`는 나중에 같은 함수를 재사용한다. |

### 완료 조건

- 깨끗한 설치에서 로그인, 실제 provider 하위 프로세스, 사용자 홈 저장소 접근 없이
  체험이 끝난다.
- 에이전트 0/1/2개, 인증 실패, 게이트 없음, 취소, 더러운 저장소에서 준비 상태와 다음
  단계를 정확히 보여 준다.
- run/room의 계획, 실행, 선택, apply 경계를 재사용하고, dry-run과 실제 실행이 일치한다.
- 테스트는 기존처럼 hermetic이며 실제 에이전트 바이너리나 tmux를 띄우지 않는다.

## 3. 꺼진 기능 안내

보드, 실행 보고서, 품질 게이트는 기본으로 꺼져 있고, 지금은 사용자가 문서를 읽어야
존재를 알 수 있다. `doctor`(그리고 `start`)에서 기능마다 상태와 켜는 법을 한 줄씩
보여 준다. 예:

```text
Quality gate: off — add commands under [gate] in syncmill.toml (e.g. commands = ["pytest -q"])
Run reports: off — set SYNCMILL_INTEGRATION__REPORT__ENABLED=true
Work-board: off — set SYNCMILL_BOARD__ENABLED=true
```

- 읽기 전용이다. 설정을 바꾸거나 기능을 자동으로 켜지 않는다.
- 켜져 있는 기능은 경로 등 현재 상태를 한 줄로 보여 준다.
- 꺼진 기능은 "준비되지 않음"이 아니다. `doctor`의 `Ready.` 판정과 `--strict` 종료
  코드는 바꾸지 않는다.
- #171과 별도로 먼저 낸다(결정 8). 이때 `doctor`의 에이전트 준비 판정도 함수로
  분리해(결정 6) `start`가 같은 판정과 안내를 재사용하게 한다.

## 4. #173 — 피드백을 후보에 묶고 그 후보만 재실행

[#173](https://github.com/memtomem/syncmill/issues/173). 순서는 #171 다음이다.

- 피드백을 후보 ID와 patch 다이제스트에 묶는다. 파일·hunk 위치는 선택이다. 변경
  요청과 질문을 구분하고, 보내기 전에 묶음을 미리 보여 준다.
- "이 후보 수리" 동작은 그 후보를 만든 에이전트만 실행하고, 기존 lineage/resume
  경로를 재사용한다. 세션을 이어갈 수 없으면 새로 시작한다는 사실과 추가 호출을
  실행 전에 보여 준다. 조용히 바꾸지 않는다.
- 결과는 새 후보로 저장하고 원래 patch와 검증 결과를 보존한다. 다시 검증하고, 다시
  명시적으로 선택·apply해야 한다. 이전 후보의 게이트 통과를 물려받지 않는다.
- 기존 전체 멤버 Room 라운드와 `continue`의 의미는 유지한다. 대상 지정 라운드는 대상
  집합을 기록하고 관계없는 후보를 재실행하지 않는다.
- 패치가 바뀌면 이전 위치를 조용히 다시 해석하지 않는다. 다시 붙이거나 파일 단위로
  바꾸게 한다.
- 피드백 작성만으로는 provider를 호출하지 않는다. 자동 무한 수리 루프는 만들지 않는다.

## 5. #190 — 측정 설계 (#171·#173 이후)

[#190](https://github.com/memtomem/syncmill/issues/190)은 코드가 아니라 측정 계획이다.
#171과 #173이 나온 뒤 아래를 정한다.

- **대조군:** 비교 기능 이전 UI(#172 기준 `3383e7c`), 또는 새 비교 화면 없이 검토한
  Room. 같은 과제를 두 조건에서 수행하고 순서를 상쇄(counterbalance)한다.
- **보고할 구간:** 검토 시작 시점은 지금 기록되지 않는다(`room compare`와 TUI 비교
  화면은 읽기 전용). `round.completed → candidate.selected`를 대리 지표로 쓸지, 선택형
  로컬 "검토 시작" 이벤트를 추가할지 정한다. 추가하더라도 compare는 기본적으로
  읽기 전용으로 유지한다.
- **잘못된 승인의 정의:** 후보 중에서 고른다. `--verify` 실패로 끝난 apply, 나중에
  되돌린 선택, 사후 검토자 판단.
- **표본 수:** 중앙값 20% 단축을 검출할 수 있는 참가자·과제 수를 정한다.
- **승자 없음:** 둘 다 실패하거나 둘 다 적합한 경우를 따로 세고, 승자를 강요하지
  않는다.
- 외부로 나가는 텔레메트리는 범위 밖이다.
